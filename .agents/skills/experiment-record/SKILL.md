# experiment-record（実験の記録）

実験の結果は、後から経緯を追え、別の人が同じ条件で再実行できる形でリポジトリに残します。PR 本文や VM 上のファイルだけに残しません。

## 手順

1. 計画: `references/record-template.md` を `docs/experiments/S<番号><英字>-<short>.md` に写します。目的、仮説、変える条件と変えない条件、採否の基準、繰り返しの回数を先に書きます。採否の基準は数値で決め、結果を見てから変えません。繰り返しは 5 回以上を基本とし、中央値と最小・最大を出します。
2. 基準の固定: 基準の commit、ホストの OS と CPU 数とメモリー、`git submodule status`、`BUILD_ROOT` などの出力先、成果物を作り直したか使い回したかを書きます。ツールの版は、実際に使われたバイナリから取ります（`emcc --version`、`node --version`、Playwright の Chromium の版、Autotools の各コマンドの `--version`）。比べる成果物の SHA-256 を記録します。`build-info.json` がある場合は、その記載とも照合します。
3. 計測器の検証: 本番の前に、計測器が正しく反応するかを確かめます。同じ条件で 2 回測って差を見る（A/A 試行）、読み戻しを壊した負の対照で失敗が出ることを見る、などを行って記録します。
4. 実行: 実行に使うスクリプトは `scripts/` や `tests/` などリポジトリ内に置きます。条件の選択は CLI 引数で受け取り、既存の出力や CSV があれば上書きせずに止めます。候補は 1 回ごとに交互に実行し、順番の影響を避けます。重い実験は CI に載せません。実行中の試行が使っているスクリプトは編集しません。コマンドと環境変数は、記録にそのまま書きます。
5. 記録: 人が読む要約は Markdown に、生の値は同じ名前の `.csv` に書きます（列は `assets/results-template.csv`）。捨てた試行も理由と一緒に残します。大きなログはコミットせず、再生成の方法と SHA-256 を書きます。CSV は 1 ファイル 1 MB までを目安にします。
6. 反映: `docs/experiments/README.md` の一覧に 1 行足し、結論を `RESEARCH.md` の該当する節に反映します。以前の記述を正すときは、消さずに訂正の経緯を書きます。PR 本文には記録へのリンクを書きます。日本語の文章は yomiyasu の lint を通します。

## 提出前の確認

- [ ] 採否の基準を、結果を見る前に書いた
- [ ] 版は、実際に使われたバイナリから取った
- [ ] 測った WASM の SHA-256 が、記録した commit から作ったものと一致する
- [ ] 計測器の検証を行い、値が 0 や全条件で同じになっていないか確かめた
- [ ] 試験が対象の機能を実際に動かしている（ログで確かめた）
- [ ] 判定に使う行や値が、負の対照では出ないことを確かめた
- [ ] 実行ログのエラーと警告を読んだ（成功の判定だけで済ませていない）
- [ ] 改善だけでなく、劣化しうる指標（大きさ、起動時間、メモリー、ビルドの時間）も測った
- [ ] 絶対値を書いた（相対値だけにしていない）
- [ ] 仮想デバイスでの値は、実機の値ではないと明記した
- [ ] 失敗・中止した試行と、その理由を残した
- [ ] 根拠に VM や個人環境のパスを書いていない
- [ ] 一覧と RESEARCH.md を更新した

落とし穴の実例と根拠は `references/pitfalls.md` にあります。
