# S14 CPU コアのプログラム実行と4ボード比較

- 状態: 実装中。正式測定は未実施。
- 関連: [T5 のライブラリー調査](../research/hdl-libraries.md)

## 目的と仮説

固定版の CPU を最小の ROM、RAM、GPIO へ接続し、実際の命令実行と4ボードの適用可否を確認します。対象は SERV、PicoRV32、NEORV32、Hazard3、VexRiscv の生成済み RTL、DarkRISCV、FemtoRV の7候補です。CPU や命令の処理を JavaScript へ移植せず、元の RTL を使います。

## 採否の基準

結果を見る前に、次を基準とします。

1. 選んだソース、必要な include、固定版、パラメーター、原ライセンスを保持し、ZIP 往復後の共通入力から処理する。
2. ROM のプログラムが値を読み、算術・分岐・RAM 書込み・読み戻し・GPIO 出力を行う。独立した検査で16回以上の出力、RAM の書込みと読み戻し、複数回の入力採取を確認する。
3. プログラム破損、reset 保持、期待値の破損、入力の固定、LED 出力の固定を、それぞれ不合格として検出する。合格の表示が負の対照に出ない。
4. Verilog は native と WASM の Icarus で終了状態・標準出力・VCD が一致する。VHDL は名前付き library と解析順を維持し、native GHDL と合成後の Verilog による検査を組み合わせる。
5. 合成後に状態、CPU データパス、メモリーへのアクセスが残り、単なる定数回路や未接続の CPU にならない。
6. 各候補を4ボードで試す。成功した組合せだけを確認済みとする。容量不足はツールの診断で裏付け、処理系の非対応や未検証と混ぜない。
7. 成功した組合せでは native/WASI の合成・配置配線と、native/Pyodide の bitstream を厳密に照合する。配置の差を正規化で隠さない。
8. 正式な測定は清浄な同一 commit と実バイナリーの hash に固定し、5回以上を交互に反復する。A/A と負の対照を先に確認する。時間、資源、メモリー、出力サイズの生データを残し、各行の状態も読む。重い反復は CI へ追加しない。

## 配線差の切り分け

9K の同じ SERV netlist を使い、各系を5回ずつ交互に実行しました。各系の中では5回とも同じ JSON となり、native / WASI の間だけに差がありました。`router2` と `--threads 1` に切り替える追加の5回ずつの試行でも、この差は解消しませんでした。いずれも診断用であり、他の処理と並行していたため、時間を正式な性能値には使いません。

router1 の arc hash に使うポインターと `size_t` を、名前の hash と固定幅の `unsigned int` に置き換える隔離案も試しました。各系5回ずつの結果は変更前と同じ hash で、配線差は解消しませんでした。この案は不採用であり、製品のビルドには追加していません。試行用のパッチは `0003-stabilize-router-arc-hashes.patch` です。

次は、Gowin の segment 選択で使う `std::unordered_multimap` の同じ座標の範囲について、標準ライブラリー間の列挙順の違いを調べます。採用条件は、同じ netlist から native / WASI が5回ずつ全て同一の JSON を生成し、既存の8候補と他の CPU の回帰検査を通ることです。比較時に順序や配線を正規化することはしません。

## segment 列挙順の追加診断

`globals.cc` の segment 候補を格納する `std::unordered_multimap` を `std::multimap` に変更した隔離ビルドでは、SERV の9K・20Kで、それぞれ native / WASI の各5回が同一の配置配線 JSON となりました。`0004-stabilize-segment-grid-order.patch` を、上流のファイルを直接変更せずにビルド時の別ファイルへ適用します。ビルド情報には、既存の `placer_heap.cc` と追加した `globals.cc` の原本、パッチ、適用後の SHA-256 を残します。

この変更を含む製品用バイナリーで、HDL 8候補と CPU の4ボード回帰を進めています。途中で、PicoRV32・4Kには別の配置差が残ると分かりました。双方の終了状態は0で、例外、実行エラー、signal はありません。LUT4 は2335/4608、DFF は984/3456、BSRAM は1/10で、容量不足には分類しません。

保存した両系のログでは、解析的配置の第36反復までは、表示された wire length の値が一致しています。第37反復では、解いた直後の値は双方11713ですが、spreading 後は native が14995、WASI が14994となり、合法化後も異なります。配置先の `NEXTPNR_BEL` にも差があるため、JSON の出力順だけの問題ではありません。表示値が一致する反復でも、生の浮動小数点数の一致までは確認できていません。

この切り分けでは、正規化をせずに次の2ファイルを比較します。検査の assertion は native を actual、WASI を expected としているため、hash の実行系を取り違えないよう、保存ファイルからも計算し直しました。

| 実行系 | 保存ファイル | JSON を読み戻した後の SHA-256 |
|---|---|---|
| native | `native-pnr.json` | `6b1deb2bb2be8a7102cf9685ed364e79d7b2ad9f8e9189b617f00edb26e8d8b9` |
| WASI | `pnr.json` | `7b6b2b78513c15828bdfd835ae0d8f73960b991a752e3dd85e8cd3ce03f8bbc8` |

追加の診断では、同じパッチを含む native の `placer_heap.cc` だけに `EIGEN_DONT_VECTORIZE` を指定しました。採用条件は、同じ入力と seed に対する各系5回の配置配線の一致、既存の HDL 回帰、CPU の各ボードの分類と pack の再確認です。数値の丸め直しや、配線の比較除外はしません。

この隔離ビルドでは、native と製品用 WASI の各5回、計10回の配置配線 JSON が、元の WASI の結果と全バイト一致しました。raw SHA-256 は `d8254b3368a94c56e9ae1e3838467377ffdc6e6872eae80faecb6694cddb247a` です。全行の status、資源、入力、ログ、バイナリーの識別情報を確認しました。他の検査と並行した診断なので、実行時間の正式な比較には使いません。

## 正式な反復測定の手順

`scripts/verify-pnr-library-matrix.mjs` は既存の HDL モードを維持し、`--kind cpu` で28組の分類を検査します。前提となる行、ZIP、netlist、配置配線、bitstream の hash と状態を読み、成功・容量超過・frontend 非対応で全組が埋まらなければ開始しません。清浄な commit、製品用バイナリー、ビルド情報、パッチ、chipdb、helper の hash を固定します。CPU モードでは実際の native / WASM Icarus の版とバイナリーも照合します。

各経路の A/A を2組ずつ先に実行し、壊した routed / capacity 入力と、意図的に誤らせた frontend 診断を拒否することを確認します。その後、routed / capacity の native と WASI を各5回以上、交互に実行します。frontend 非対応の行は、実際の Icarus の解析失敗を各5回確認し、合成・配置配線や性能の成功として扱いません。

CSV の `matrix_` 列は、前提の全体回帰で得た合成、下位化の実行、構造保持、pack の値を表します。この driver で5回ずつやり直した値ではありません。時間と WASI メモリーの中央値・最小・最大は、正常な配置配線の本試行だけで集計します。CPU と HDL の driver を並行する場合は、`EXPERIMENT_CONCURRENT_WORKLOAD` と host の load average に記録します。この負荷条件の時間から、隔離した性能改善を主張しません。採否は正しさと分類の一致を優先します。重い反復は CI へ追加しません。

## 初回の正式反復で見つかった負の対照の不備

commit `6df08e89e5d8019f16b37e8a0d56ab58d6102d6f` の3回目の全体回帰は、CPU が bitstream まで成功した18組、容量超過6組、frontend 非対応4組、検査の失敗0組でした。HDL は32組全て成功しました。各行の状態、資源、終了状態、例外、signal、時間、メモリー、入力 ZIP と生成物の hash を読みました。frontend 非対応や容量超過を bitstream の成功とは扱いません。この入力から、同じ清浄な commit で最初の正式反復を開始しました。

CPU の routed A/A は native / WASI 計20回が一致しました。しかし、負の対照で最初の `LUT4` の種類を未知の種類へ変更すると、SERV の wide MUX が必要とする入力 LUT も壊れました。nextpnr は想定した未知の種類の配置失敗より先に、`ERROR: Bad MUX2 node:cpu.cpu.alu.add_cy_r_LUT3_I1_F_MUX2_LUT5_I1_I0_LUT4_F` と診断しました。両系の全10回は非成功で、配置配線の出力もありませんでしたが、想定した診断を検証できないため driver は終了状態1で停止しました。CPU の正式測定は、この試行では未完了です。失敗のログと入力は上書きしません。

負の対照は、既存セルの種類、接続、順序を変えず、接続のない未知のセルを1個追加する方式へ修正します。予約した名前が既存なら停止します。判定は緩めず、追加したセル名と未知の種類を含む唯一の配置エラー、非成功の終了状態、予期した例外、signal と配置配線出力がないことを必要とします。単体検査では既存の LUT / MUX と入力全体が不変であることを確かめ、別セル、別の種類、MUX の不具合、余分なエラー、成功した終了、signal、予期しない実行エラーを拒否します。修正を含む清浄な commit で、CPU と HDL の正式反復を新しい出力先へやり直します。前提の全体回帰は上記 commit の入力であることを分けて記録し、再実行したと書きません。
