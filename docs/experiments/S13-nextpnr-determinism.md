# S13 nextpnr の配置結果の再現性

- 状態: 完了。候補2を製品用に採用。HDL 8候補×4ボードの正式な比較を通過した。
- 日付: 2026-11-01
- 目的: T5 の HDL 8候補で見つかった native / WASI の配置差を切り分ける。

## 探索試行で分かったこと

同じ Yosys netlist と制約を与えると、UART の4ボードで native と WASI の配置結果が異なりました。合成 JSON と資源の数は一致し、両方の配置配線は終了コード0でした。Tang Nano 1K で実行順を交互にして5回ずつ試すと、各実行系の結果は5回とも同じで、実行系の間だけに差がありました。

Eigen のベクトル化を無効にした native の比較用バイナリーも5回試しました。結果は元の native と同じでした。これだけでは数値計算の差を原因と判断できません。

ソースを読むと、`common/place/placer_heap.cc` の `find_control_set_candidates()` に距離の比較式の誤りがありました。比較相手の x 座標を使うはずの項が y 座標になっています。同じ要素を比較して真を返す入力があり、整列に必要な厳密弱順序を満たしません。これが今回の配置差の原因かどうかは、以下の比較で確かめます。

## 修正候補の基準（候補の実行前に固定）

1. 変更は比較相手の `b.y` を `b.x` に直す1行だけとする。`stable_sort`、seed、配置のアルゴリズム、最適化設定は変えない。
2. 元の比較式は反射性の否定を検査する負の対照で失敗し、修正後は自己比較・非対称性・独立した距離順の検査を全て通ること。
3. native と WASI の修正候補を、元のオブジェクトファイルから対象の翻訳単位だけを差し替えて作る。元のバイナリーと submodule は書き換えない。
4. UART は4ボードで各実行系を5回ずつ、新しい作業ディレクトリーで交互に実行する。同じ実行系での再現性と実行系間の JSON 完全一致を必要条件とする。資源の数も一致させる。
5. 採用前に、HDL 8候補×4ボード、既存の nextpnr 比較、shim と Node WASI の比較、native / Pyodide pack を再検査する。回路や JSON のキー順を正規化して差を消さない。
6. 出力サイズ、実行時間、メモリーの測定範囲、失敗した試行を記録する。実機・実ブラウザーの確認とは区別する。

## 再現用のコードと記録先

- `scripts/diagnose-pnr-layout.mjs`: 同じ入力の5回比較。入力とバイナリーの SHA-256、作業ツリー、ホスト、各回のログと CSV を保存する。
- `scripts/build-pnr-scalar-probe.py`: CMake が生成したコンパイル・リンクの引数から隔離した比較用バイナリーを作る。製品のビルドや配布には使わない。
- パッチ: `patches/nextpnr/0001-fix-control-set-distance-comparison.patch`。

探索試行は未コミットの検査コードを含むため、提出 commit の検証としては扱いません。正式な結果と再実行手順は後半に記します。

## 候補1の結果と、候補2の基準

比較式の修正候補は Tang Nano 1K で5回ずつ実行しました。各実行系の配置は元のバイナリーと同じで、実行系間の差は解消しませんでした。自己比較を含む検査は、元の式の誤りと修正後の成功を確認できましたが、今回の差を直す効果はありません。候補1は既定へ採用していません。

呼び出しの条件も確認しました。`common/place/placer_heap.h` の `ff_bel_bucket` は空が初期値です。`himbaechel/uarch/gowin/gowin.cc` の `GowinImpl::configurePlacerHeap()` はこの値を変更しません。`placer_heap.cc` は空でない場合だけ control set の候補を探すため、この固定版の Gowin では誤った比較式を使う経路に入りません。別のアーキテクチャーの修正としては検討の余地がありますが、今回の製品用パッチには重ねません。

もう一つの候補は `cut_region()` の同じ座標を持つセルの扱いです。元の `std::sort` は同じキーの順番を保つことを保証しないため、C++ 標準ライブラリーが異なる実行系で並びが変わりえます。候補2では、この呼び出し1か所だけを `std::stable_sort` へ変更し、入力の順番を保ちます。比較式や、それ以外の配置の条件は変更しません。

候補2の実行前の基準は、元の整列で同じキーの順番が変わる負の対照を確認し、変更後は入力順を保つこと、UART の4ボードで各5回の JSON 完全一致を得ること、採用前に8候補×4ボードと既存の回帰検査を通すことです。候補1のパッチは重ねず、独立して比べます。速度の改善を目的とせず、サイズ・時間・メモリーへの影響は記録します。

候補2のパッチは `patches/nextpnr/0002-stabilize-equal-coordinate-cuts.patch` です。隔離したバイナリーでは、UART の4ボードで各実行系を5回ずつ、計40回の配置 JSON が一致しました。続く8候補×4ボードの検査も33/33件が成功しました。これは製品用バイナリーの検証とは分けます。

## 製品用ビルドへの接続と、正式な比較の基準

元の製品用 native / WASI バイナリーと build-info は、変更前にコピーして SHA-256 を照合しました。上流ファイルを直接変更せず、`scripts/prepare-pnr-source.py` で入力を隔離して候補2だけを適用します。元のソース、パッチ、変更後ソース、ビルド補助コードの SHA-256 を build-info に保存し、実ファイルとも照合します。

nextpnr の heap placer は、実行ファイルの直接のソース一覧ではなく、`nextpnr_place` の `INTERFACE_SOURCES` に含まれます。`scripts/nextpnr-patches.cmake` は root project の構成の最後に対象1件だけを差し替えます。対象がない場合、複数ある場合、パッチを適用できない場合は失敗させます。候補1は製品用ビルドでは使いません。

製品用バイナリーの正式な比較では、次を確認します。

1. 製品用の native / WASI を通常のビルド手順で作る。再利用したキャッシュと、作り直した範囲を記録する。
2. UART は4ボードで native / WASI を各5回実行し、全40回の成功、同じ実行系での再現性、実行系間の配置 JSON 完全一致を求める。
3. HDL 8候補×4ボードで、合成・配置配線・pack・IDCODE・bitstream の厳密な比較を再実行する。
4. 配置済みの JSON を使う反復診断は、同じ netlist と制約から配置配線をやり直す。合成や pack を5回反復した結果とは扱わない。
5. 同じ製品用バイナリーの A/A 試行を新しいディレクトリーで2組実行し、配置を照合する。壊した netlist は両方の実行系で失敗し、診断全体も非ゼロで終わることを求める。
6. 生の CSV に終了状態、配置の SHA-256、実行時間、WASI の最終 linear memory を保存する。native の RSS、ブラウザーの起動時間、実機の時間は測ったことにしない。

実行時間は native のプロセス起動と配置配線、または WASI のインスタンス生成と配置配線を含みます。WASM module のコンパイルは含みません。実行系の順番は反復ごとに逆転します。基準版と候補版を組ごとに実行した値から、パッチ単独の速度の差は結論しません。採用の目的は配置結果の安定性であり、高速化ではありません。

## 失敗した準備試行

- CMake 3.22 では上流の要求を満たせず、構成に失敗した。固定した CMake 3.31 でやり直した。
- `CMAKE_PROJECT_INCLUDE` が subproject でも呼ばれ、Gowin target が見つからなかった。root project 以外では処理しないようにした。
- 実行ファイルの直接のソース一覧には heap placer がなく、差し替え数の検査で失敗した。上記の INTERFACE target に変更した。
- 製品用 native のリンク中に回帰検査を並行実行し、起動時の EACCES で5件が失敗した。ビルド終了後、同じ検査を21/21件成功でやり直した。失敗した実行を製品の配置差とは扱わない。
- 資源表の検査を強める際、末尾の改行を空行と誤認することを負の対照で見つけた。表の終わりを確認する処理を修正した。

## 正式な結果

先行する全工程の検査は33/33件成功、終了コード0でした。32組で ZIP 往復、VHDL の名前付きライブラリー、合成、配置配線、native / Pyodide pack の `.fs` バイト一致と IDCODE を検査しています。合成から pack までの各工程は各組1回であり、以下の5回反復と混同しません。元の32件の全フィールドは [S13-hdl-builds.csv](S13-hdl-builds.csv) に保存しました。`peak_rss_so_far_kib` は同じ Node プロセスのその時点までの高水位で、個々の工程や native nextpnr の RSS ではありません。

正式な反復は32/32組、計320回成功しました。同じ実行系での再現性と実行系間の配置 JSON 一致を全て通りました。A/A は UART / 1K の新しい出力先2組、計20回が成功し、両組の配置も一致しました。負の対照は保持された LUT4 を `S13_UNKNOWN_CELL` に変え、native / WASI 各5回を全て拒否しました。両実行系の計10回が全て失敗し、診断も非ゼロで終わっています。エラーには変更したセル型が含まれます。親ドライバーはこの期待どおりの失敗を確認して終了コード0で終わりました。

全35組の metadata / summary のハッシュ、350回の result JSON、標準出力、標準エラー、CSV の全23列を照合しました。通常実行340回にエラーや警告はなく、エラー10件は全て上記の負の対照でした。CSV の `failed` 10行は残し、`valid=false` としています。これらを性能の集計に入れていません。

### 判断と限界

同じ座標のセルの入力順を保持する候補2を採用します。確認した範囲は、この固定版・8代表回路・4ボード・同じ seed です。任意の設計での同一性を証明したものではないため、回帰検査の厳密な比較は残します。時間・メモリー・資源の絶対値は記録しましたが、基準版との対をなす5回測定ではないため、パッチ単独の速度やメモリーの改善は主張しません。

資源の使用数は4ボードとも、Colibri が LUT4 / DFF = 8 / 4、hdl-modules が15 / 10、libfpga が10 / 7、Open Logic が22 / 15、AXI が28 / 19、AXIS が15 / 12、Ethernet の CRC が47 / 24、UART が217 / 81でした。BSRAM は全て0です。`.fs` は1K が351,954、4K が1,167,294、9K が2,069,320、20K が4,618,782 bytes でした。対応の判断は選んだ部品と設定の範囲に限り、ライブラリー全体の確認とは扱いません。

反復ドライバーと大きな生ログは CI では実行・保存しません。CI には元ソースの保全、パッチの適用、比較式、同じキーの入力順、資源表の負の対照など軽い検査だけを載せます。CPU 7候補、画面操作、実ブラウザーでの性能、実機の検査はこの記録の対象外です。Tang Nano の実機は本リポジトリでは試していません。
