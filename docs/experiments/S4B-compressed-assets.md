# S4B 大きい資材の圧縮形式と展開時間の比較

- 状態: 完了
- 日付: 2026-10-27
- 担当: Devin
- 関連: `RESEARCH.md` の「配信の大きさと配信先」節

## 目的と仮説

初回に読み込む資材（ボードにより約 104〜115 MB、圧縮前）を減らすために、gzip、zstd、xz を比べます。gzip はブラウザーの `DecompressionStream` で展開し、zstd と xz は本リポジトリで WASI SDK 34 からビルドした展開器（`scripts/build-decoders.sh`）で展開します。zstd と xz は gzip より約 3 割小さくなるので、展開時間を足しても初回の完了は早くなると予想しました。

## 採否の基準（結果を見る前に書く）

- 対象: 各ボードで初回に読む大きい 5 つ（`yosys.wasm`、`nextpnr-himbaechel-gowin.wasm`、`yosys-share.tar`、`pyodide.asm.wasm`、そのボードの chipdb）。判定は Tang Nano 20K で行い、ほかのボードも同じ方法で出します。
- 推定時間 = 圧縮後の大きさ × 8 ÷ 帯域 + Chromium での展開時間の合計の中央値（5 回）。帯域は 10 Mbps と 50 Mbps です。転送は計算で出し、帯域を絞った実測はしません。方式で変わるのは大きさと展開時間だけで、転送の時間は大きさで決まるためです。
- 展開器の WASM の大きさ（gzip 後）も転送量に足します。
- zstd か xz を採るのは、次をすべて満たすときです。満たさなければ gzip にします。
  1. 50 Mbps の推定時間が gzip より 10% 以上短い。
  2. 5 つの展開時間の合計の中央値が 3 秒以下。
  3. 全回で展開後の SHA-256 が元の資材と一致する。
  4. 圧縮データの中央の 1 byte を壊した負の対照で、例外か SHA-256 の不一致になる。
- zstd と xz がともに満たし、50 Mbps の推定時間の差が 5% 以内なら、展開が速い zstd を採ります。差が 5% を超えれば短いほうを採ります。

## 手順

```sh
scripts/build-decoders.sh
scripts/build-web.sh
scripts/prepare-compressed-assets.sh dist
python3 dist/serve.py --port 8231 &
node scripts/bench-decompress.mjs --base-url http://127.0.0.1:8231 --repeats 5 --out docs/experiments/S4B-compressed-assets.csv
```

計測は展開の呼び出しだけを `performance.now()` で囲みます。取得と SHA-256 の検査は計測の外です。圧縮データは取得時に、大きさと SHA-256 を `index.tsv` と照合します。

## 計測器の検証

- 全 120 回（3 形式 × 8 資材 × 5 回）で、展開後の SHA-256 が元の資材と一致しました。
- 負の対照: `yosys.wasm` の圧縮データの中央の 1 byte を反転すると、3 形式とも例外になりました。gzip は `DecompressionStream` が `Failed to fetch` の TypeError を出し、zstd は decoder がエラーコード -2、xz は -3 を返しました。
- 展開時間は形式と資材ごとに異なり、0 や全条件で同じ値にはなっていません。回ごとのばらつきは、最小と最大で 1 割程度でした。

## 結論

基準を満たしたのは zstd です。20K の 50 Mbps の推定は gzip の 5.23 秒に対して 3.43 秒（34% 短い）で、展開の合計は 359 ms でした。xz は 4.98 秒で gzip より 5% 短いだけで、基準 1 を満たしません。xz は zstd より 10% 小さいものの、展開が約 6 倍遅いためです。zstd の展開は gzip（ブラウザー標準）より速く、WASM の展開器を使う不利はありませんでした。

gzip は gzip 1.14 の `-9` で圧縮しました。libdeflate の最高レベルにすると gzip -9 より約 5% 小さくなります（別に測った大きさ）が、それでも 20K の 50 Mbps の推定は 4.9 秒前後で、結論は変わりません。

## 失敗・中止した試行

- 帯域を絞った Chromium での実測は、計画の段階で取りやめました。理由は「採否の基準」に書きました。
- Zopfli と Brotli は大きさだけを測り、本実験には入れていません。Zopfli は libdeflate と同じくらいの大きさで圧縮が非常に遅く、Brotli は Chromium 156 の `DecompressionStream` で展開できないためです。

## 限界

- 1 台の VM の headless Chromium での値です。CPU の遅い端末では展開時間が延びます。
- 推定時間は転送を計算で出しており、HTTP の往復や並列の取得を含みません。
- 展開器の WASM のメモリーは、展開した最大の資材（`yosys.wasm`）の分まで増えたまま残ります。資材の取得経路に組み込むときに扱います。
